## 5. Keys, identity and document numbering

There are **four** distinct numbering mechanisms in arzi, and they are not interchangeable:

| # | Mechanism | Scope | Generated by | Race-safe? |
|---|---|---|---|---|
| A | Surrogate key `*_SSN` | per table | SQL Server `IDENTITY` | yes (allocation), **no** (retrieval — §5.2) |
| B | Document number (`M_Sanad`, `AF_Factor`, `FM_Factor`, `DM_Sanad`) | per **fiscal year** | client-side `SELECT MAX(...)+1` | **no** |
| C | Account code (`S_Ko`, `S_Mo`, `S_Ta1`, `S_Ta2`) | global (master data) | client-side `SELECT MAX(...)+1` with seed | **no** |
| D | External receipt serial (`NR_Serial` / `@GhabzNo`) | external DB | **not generated here** — looked up and validated | n/a |

### 5.1 Surrogate keys — `*_SSN`

Despite the name, `SSN` is **not** a social security number (see `docs/01-glossary.md` §6): it is the
surrogate primary key, an `int IDENTITY(1,1)` in SQL Server. The Delphi side sees them as
`TAutoIncField`, which is exactly how ADO surfaces an identity column. Enumerated from the `.dfm`
field lists:

| Legacy key | Table | Proposed |
|---|---|---|
| `M_SSN` | `Moein` (voucher lines) | `voucher_lines.id` |
| `DM_SSN` | `DMoein` (voucher headers) | `vouchers.id` |
| `S_SSN` | **`Sarfasl`** (chart of accounts) | `accounts.id` |
| `S_SSN` | **`DCheck`** / `DFish` / `DCheck2` (treasury) — *same column name, different table* | `cheques.id` / `deposit_slips.id` |
| `AF_SSN` | `Anbar_Factor` (invoice header) | `invoices.id` |
| `CM_SSN` | cheque-book master | `cheque_books.id` |
| `TM_SSN` | petty-cash header | `petty_cash_documents.id` |
| `FM_SSN` | external `Anbar.dbo.FactorMaster` | external |
| `FD_SSN` | external `Anbar.dbo.FactorDetail` | external |
| `NR_Serial` | external `Rppc_Solution.dbo.NewRamz` | external (`FactorPesteh_U.dfm:29`) |

Note the `S_` prefix collision: `S_SSN` on `Sarfasl` means "account id", `S_SSN` on `DCheck` means
"cheque id", and `Moein.M_Code` stores a **`Sarfasl.S_SSN`** (`FactorPesteh_U.pas:229-230`:
`Update moein Set M_Ko=S_Ko, ... From Sarfasl Where M_Code=S_SSN`). The rebuild must disambiguate
these; see §14.

**There is no natural key on any transactional table.** Uniqueness of a document number within a
year is an application convention with (as far as the source shows) no database constraint behind
it — see §12.

### 5.2 Retrieving the identity just inserted — `@@IDENTITY`

Two places need the key of the row they just inserted, and both use the **scope-unsafe**
`@@IDENTITY`:

`FactorPesteh_U.pas:203`
```sql
Declare @FMSSN int Set @FMSSN=@@Identity
```

`CheckBargashtu.pas:218` (identical pattern in `CheckDaryaft2U.pas`, `CheckEsterdadU.pas`,
`CheckVosoolU.pas`)
```sql
 Commit
 Set @Tag = @@Identity
```

`@@IDENTITY` returns the last identity value generated **in the session, in any table, including
inside triggers**, whereas `SCOPE_IDENTITY()` is confined to the current scope. If any of these
tables ever gains an `AFTER INSERT` trigger that writes to another identity table, `@Tag` silently
becomes the wrong row's key and the voucher lines link to the wrong cheque. This is latent, not
currently firing (no triggers are visible in this repo — but see §12: triggers cannot be ruled out
without a live-DB dump).

Note also that in `CheckBargashtu.pas:217-219` the `Set @Tag = @@Identity` is placed **after** the
`Commit`, so the value survives, but the second `Begin Transaction` block that consumes `@Tag`
(`:220-243`) is a *separate* transaction. If the second block fails, the `DCheck2` row from the
first block is already committed and the ledger entries are missing — a torn document. See §9.

### 5.3 Document numbers — `SELECT MAX(...) + 1`

#### 5.3.1 Voucher number (`M_Sanad` / `DM_Sanad` — `شماره سند`)

`Dmu.pas:1242-1251`:

```pascal
function TDM.New_Sanad: integer;
begin
    Q1.Close;
    Q1.ConnectionString := Ado.ConnectionString;
   Q1.SQL.Clear;
   Q1.SQL.Add('  Select isnull(Max( M_sanad ),0 )+1 as NewSanad From moein Where M_COid='+inttostr(DM.CO_ID) );
   Q1.Open;
   Result := Q1.FieldByName('NewSanad').AsInteger;
   Q1.Close;
end;
```

- Scoped to the fiscal year (`M_COid`), so voucher numbers restart at 1 each year.
- Reads `Moein` (the **lines** table), not `DMoein` (the header table) — the header numbering at
  `MoeinToRU.pas:264` reads `DMoein` instead:
  ```sql
  Select isnull(Max(DM_Sanad) , 0)+1 As N From DMoein Where DM_Coid=<year>
  ```
  **Two different sources of truth for the same number.** If a header exists with no lines (or vice
  versa) the two allocators disagree.
- `Q1` has no design-time `Connection`; the caller assigns `ConnectionString` (`Dmu.pas:1244-1245`),
  so this runs on its own connection and its own implicit transaction (§1.6, §9).

#### 5.3.2 Voucher number with same-day reuse — `Get_NewSanad_DateID`

`Dmu.pas:1461-1477` — the treasury/inventory modules do not always allocate a fresh voucher; they
**append to an existing open voucher of the same date and kind**:

```pascal
function TDM.Get_NewSanad_DateID( F_Date:String; IDList:String ): Integer;
begin
    Result := New_Sanad;                                     // fallback: a brand-new number
    ...
    Dm.Q1.SQL.Add(' Select isnull( Max(M_Sanad) , 0 ) as S  ');
    Dm.Q1.SQL.Add('   From Moein ');
    Dm.Q1.SQL.Add('   Where M_Tx=0 and M_Coid='+ inttostr(Dm.CO_ID) );
    Dm.Q1.SQL.Add('   and M_ID in( ' + IDList+ ')' );
    Dm.Q1.SQL.Add('   and M_Date='+ QuotedStr(F_Date) );
    Dm.Q1.Open;
    if Dm.Q1.FieldByName('S').AsInteger >0  then
            Result := Dm.Q1.FieldByName('S').AsInteger;       // reuse
    Dm.Q1.Close;
end;
```

- `M_Tx = 0` means **draft / not finalised** (`در حالت تحرير`, cf. `Dmu.pas:1301-1307`). A finalised
  voucher (`M_Tx > 0`) is never reused.
- `IDList` is a comma-separated list of `M_ID` **source-module codes**. Observed call sites:
  - `CheckBargashtu.pas:197` — `'21,22,23,24,25,26,27,28,29'` (cheque operations)
  - `AnbarFactorU.pas:593` — `'1,2,3,4,5,6,7,8,9'` (inventory invoices)

  So each functional family shares one daily voucher. `IDList` is **string-concatenated straight
  into the SQL** — an injection surface if it ever becomes user-controlled (§13).
- **Two round trips, no transaction**: `New_Sanad` runs first (allocating a candidate), then the
  reuse probe. Between them another workstation can insert.

`Get_SanadDateID_Valid` (`Dmu.pas:1494-1521`) is the corresponding guard used before appending to a
number the user typed: the voucher must either not exist, or be a draft (`Get_SanadMaxTX = 0`,
`Dmu.pas:1538-1550`), on the same date (`Get_SanadDate`, `Dmu.pas:1480-1492`), and already contain
at least one line from the same `IDList`.

#### 5.3.3 Inventory invoice number (`AF_Factor` — `شماره فاکتور`)

`Dmu.pas:1253-1262`:
```sql
Select isnull(Max( AF_Factor ),0 )+1 as NewFactor From Anbar_factor Where AF_COid=<year>
```
Same pattern, same race, also per fiscal year.

#### 5.3.4 External invoice number (`FM_Factor`) — the one server-side allocation

`FactorPesteh_U.pas:194-195` is the **only** allocator that runs inside the same batch as the
insert:

```sql
Declare @FmFactor int Set @FMFactor= isnull( ( Select Max(FM_Factor)+1 From Anbar.Dbo.FactorMaster
        Where FM_Coid=@Coid And FM_Anbar=17) , 1700001)
```

- Seeded at `1700001` — warehouse **17**, sequence `00001`. The number therefore encodes the
  warehouse in its leading digits, a semantic that must survive the rebuild.
- Runs inside `Begin Transaction` (`FactorPesteh_U.pas:181`) … `Commit` (`:231`), so it is
  *atomic*, but under the default `READ COMMITTED` isolation it is still **not serialisable**: two
  concurrent transactions can both read the same `MAX` and both insert. Only `SERIALIZABLE`, a
  `HOLDLOCK`/`UPDLOCK` hint, or a real sequence would close it.

#### 5.3.5 Chart-of-accounts code allocation

`SNewu.pas:553-586` and `S_KolU.pas:258-291` (duplicated logic in two screens):

```sql
Select isnull( Max(S_ko)+1  , 111 ) as code From Sarfasl                      -- general ledger level
Select isnull( Max(S_mo)+1  , 111 ) as code From Sarfasl ...                  -- subsidiary level
Select isnull( Max(S_Ta1)+1 , 1   ) as code From Sarfasl ...                  -- analytic level 1
Select isnull( Max(S_Ta2)+1 , 1   ) as code From Sarfasl ...                  -- analytic level 2
```

Seeds: `111` for the two upper levels, `1` for the two analytic levels. `Sarfasl` is **not**
year-scoped (§1.4), so these are global. The display width of each segment is configurable per
fiscal year via `Base.NO_Ko` / `NO_Mo` / `NO_Ta1` / `NO_Ta2` and applied by zero-padding at
`Dmu.pas:1199-1223` — the code is *stored* as separate integers and only *rendered* as
`Ta2-Ta1-Mo-Ko` + name. See `docs/03-accounting-core.md`.

### 5.4 `B_SelectSerial` and `Get_Serial` — a lookup, not a generator

Despite the name, **`B_SelectSerial` allocates nothing.** It is a stored procedure on the *external*
`Rppc_Solution` connection (`Dmu.dfm:1143-1164`, `Connection = ADO_RPPCSOLUTION`) taking one input
parameter `@GhabzNo integer` (`قبض` = receipt note) and returning the matching purchase-receipt row.

`Get_Serial.pas:51-76` is the whole consumer:

```pascal
  Dm.B_SelectSerial.Parameters.ParamByName('@GhabzNo').Value := Serial.IntValue;
  Dm.B_SelectSerial.Open;
  if Dm.B_SelectSerial.RecordCount <> 1 then
  Begin
    MessageDlg('قبض مورد نظر يافت نشد', MtError, [MbOk], 0);   // "the requested receipt was not found"
    ...
  End;
  if Dm.B_SelectSerial.FieldByName('SerialNoPsnBts').AsInteger <> Jari.intvalue Then
  Begin
    MessageDlg('اطلاعات قبض و جاري مطابقت ندارد', MtError, [MbOk], 0);  // "receipt and current-account data do not match"
    ...
  End;
  Tag := Serial.intvalue;
```

So: the operator types a **receipt number** and a **current-account number**; the procedure must
return exactly one row; the returned `SerialNoPsnBts` must equal the typed current-account number.
Only then is the receipt number accepted. It is a two-factor validation of an externally issued
serial. Invoked from `Lab.pas:46-49`; the accepted value is smuggled out through the form's `Tag`
property.

**What must be extracted from the live DB:** the body of `B_SelectSerial` and the definition of
`Rppc_Solution.dbo.NewRamz` (see §3).

### 5.5 Numbers that are *not* generated

- **Cheque number `S_CheckNo`** — `varchar(15)` (`Dmu.dfm:936-939`), transcribed from the physical
  cheque. Never generated. It is a **string**, not an integer, so it can carry leading zeros and
  bank-specific formats.
- **Bank account / SHEBA / card numbers** — validated (`TDM.IsValidShaba`, `Dmu.pas:196-214`, ISO
  13616 mod-97; `TDM.IsValidKart`, `Dmu.pas:216-240`, Luhn) but never generated.
- **`CO_ID`** (fiscal year) — typed by the operator when creating a new year, defaulted to
  `previous + 1` (`MakeNewU.pas:73`) and rejected if it already exists (`MakeNewU.pas:107-113`).
- **"Today"** — allocated by the server, not the client (`Dmu.pas:1232-1239`, §6.2).

### 5.6 Race conditions in the current design

| # | Race | Where | Consequence |
|---|---|---|---|
| R1 | `MAX(col)+1` read on one connection, `INSERT` on another, no lock, no transaction | `Dmu.pas:1247`, `Dmu.pas:1258`, `MoeinToRU.pas:264`, `SNewu.pas:553-586`, `S_KolU.pas:258-291` | two workstations receive the **same** voucher / invoice / account number |
| R2 | Time-of-check → time-of-use gap. The allocated number is placed in a UI edit box and only written when the operator presses Save — potentially minutes later | `AnbarFactorU.pas:593` (`AF_Sanad.intValue := DM.Get_NewSanad_DateID(...)`), `CheckBargashtu.pas:197` | duplicate numbers are the *normal* outcome under two concurrent operators, not an edge case |
| R3 | `Get_NewSanad_DateID` issues **two** statements on a connection-per-call query object | `Dmu.pas:1461-1477` + `Dmu.pas:1242-1251` | the "reuse the open daily voucher" decision is made against a snapshot that can be stale by the time of insert; two operators both create "today's" voucher |
| R4 | `@@IDENTITY` instead of `SCOPE_IDENTITY()` | `FactorPesteh_U.pas:203`, `CheckBargashtu.pas:218` and siblings | a future trigger silently mislinks documents |
| R5 | Two sequential transactions where one logical document is written | `CheckBargashtu.pas:207-243` (`Commit` … `Begin Transaction` … `Commit`) | a failure between them leaves a treasury record with no ledger entries |
| R6 | `MAX+1` inside a transaction but under `READ COMMITTED` | `FactorPesteh_U.pas:181-231` | atomic but not serialisable; duplicate `FM_Factor` still possible |
| R7 | Two different allocators for the same voucher number (`Moein` vs `DMoein`) | `Dmu.pas:1247` vs `MoeinToRU.pas:264` | header-only or line-only vouchers desynchronise the sequence |
| R8 | No uniqueness enforcement observable in the source | everywhere | nothing stops R1–R7 from landing; duplicates are discovered only when a report double-counts |

There is **no** advisory-lock, no `sp_getapplock`, no `UPDLOCK`, no `SERIALIZABLE`, and no
"counters" table anywhere in the codebase. See §9 for what `LockUnit.pas` actually does (it does
**not** protect numbering).

### 5.7 Proposed PostgreSQL replacement

| Legacy mechanism | Proposed replacement | Notes |
|---|---|---|
| `int IDENTITY(1,1)` `*_SSN` | `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | widen `int`→`bigint`; there is no reason to inherit a 2.1-billion ceiling. Use `GENERATED ALWAYS` so the application cannot supply one by accident. |
| `@@IDENTITY` | `INSERT ... RETURNING id` | exact, scope-safe, one round trip, and works inside the transaction. Removes R4 entirely. |
| `New_Sanad` (`MAX(M_Sanad)+1` per year) | `voucher_number integer NOT NULL` allocated from a **per-fiscal-year counter row**: `UPDATE fiscal_years SET next_voucher_number = next_voucher_number + 1 WHERE id = $1 RETURNING next_voucher_number - 1`, inside the same transaction as the insert | The `UPDATE ... RETURNING` takes a row lock, so it serialises correctly and yields **gapless** numbering — which accounting practice in Iran requires. A bare `SEQUENCE` is *not* equivalent: sequences are non-transactional and leave gaps on rollback. |
| `New_AnbarFactor` (`MAX(AF_Factor)+1`) | same counter pattern, `fiscal_years.next_invoice_number` | |
| `MoeinToRU.pas:264` (`MAX(DM_Sanad)+1`) | **deleted.** One allocator only, on the header (`vouchers`), with lines carrying `voucher_id` | closes R7 |
| `Get_NewSanad_DateID` (reuse today's draft) | a single statement inside the transaction: `SELECT id FROM vouchers WHERE fiscal_year_id=$1 AND voucher_date=$2 AND status='draft' AND source_module = ANY($3) FOR UPDATE` → if none, allocate | `IDList` becomes a typed `smallint[]` bind parameter, killing the injection surface |
| `FM_Factor` seeded at `1700001` | keep the semantics: `warehouse_id * 100000 + per_warehouse_counter`, counter held in a `warehouse_counters` row, allocated with `UPDATE ... RETURNING` | preserve the number format — printed documents in the field carry it |
| `MAX(S_Ko)+1` etc. | `UPDATE account_code_counters SET next_value = next_value + 1 WHERE level = $1 RETURNING next_value - 1`, seeds `111 / 111 / 1 / 1` | still a *suggestion* in the UI — the operator can override, so keep the counter advisory and enforce uniqueness with a constraint |
| Uniqueness | **add real constraints**: `UNIQUE (fiscal_year_id, voucher_number)` on `vouchers`, `UNIQUE (fiscal_year_id, invoice_number)` on `invoices`, `UNIQUE (general_ledger_code, subsidiary_code, analytic1_code, analytic2_code)` on `accounts` | closes R8. Verify against production data first — existing duplicates will block the migration and must be reconciled with the business owner (§12). |
| `B_SelectSerial` | an integration endpoint (HTTP or a read-only FDW/dblink to the external system) with the same two-factor check: exactly one row, and `SerialNoPsnBts = <typed current-account number>` | do **not** re-implement the external system's numbering |
| Transaction boundaries | one document = **one** transaction, `READ COMMITTED` is sufficient once counters are used, with `SERIALIZABLE` reserved for the year-end routines | closes R5, R6 |
| Time-of-check/use (R2) | allocate the number **at save time**, inside the transaction, never when the form opens. Show `(new)` in the UI until the document is persisted. | closes R2 and R3. This is a **user-visible behaviour change** — the operator no longer sees the number before saving — and therefore needs approval (§13). |
